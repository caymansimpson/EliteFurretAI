## Problem

These TODOs accumulated across the config + adjacent files and were a mix of: dead
comments to delete, fields to retire, knobs to promote to constants, doc gaps, and YAML
redundancy. The user wanted them resolved in tiers — easiest first — rather than left
in place while the harder functional TODOs (forced-switch guardrail, DISABLE/ENCORE in
`battle_iterator`, inference order-of-ops) get worked on.

## Reasoning

- **Always-on mixed precision**: the user explicitly said "make mixed_precision
  default and constant behavior, and then remove it from all configs". Gating scaler
  creation on `str(self.device).startswith("cuda")` keeps CPU tests passing
  (`GradScaler` is CUDA-shaped; CPU autocast doesn't need one) while removing the
  knob from the user surface.
- **`MODEL_ARCH_CONFIG_KEYS` pruning**: removing the two flag fields from
  `ArchitectureConfig` without pruning them from `MODEL_ARCH_CONFIG_KEYS` would have
  silently broken every resume/initialize_from path that loads an older RL checkpoint
  (because `flat_model.get(...) == None ≠ True == flat_checkpoint.get(...)`). Pruning
  the keys declares "this is no longer part of the architecture identity from the RL
  side".
- **Supervised side untouched**: the supervised pipeline still has live ablations
  that toggle these flags (e.g. `ablation_a1_no_transition.yaml`). The RL config does
  not, so removing them there is unilateral; touching the supervised side would have
  expanded scope.
- **`dedicated_vgcbench_workers` removal**: the field defaulted to 0 and was off in
  every config, so deleting it is a pure cleanup. If the partition behavior is ever
  needed again it would be cleaner to re-introduce as a curriculum-weight override.
- **`easy_test.yaml` pruning**: the TODO explicitly asked for default-redundant keys
  to be removed; doing it now reduces noise without behavior change. A few keys that
  match defaults were kept where they were grouped with comments that still serve
  the reader (e.g. the `max_concurrent_battles_per_player: null` block has rationale
  worth preserving).
